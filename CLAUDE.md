# Anora Nazar

Шлюз проверки заявки на кредит для финала WIUT 2026 (партнёры — MKBANK и ЦБ). Перед любой выдачей узел даёт зелёный, жёлтый или красный уровень с причинами и выдаёт разрешение, по которому банк двигает деньги. Продукт закрывает три слепые зоны обязательных проверок: воля заёмщика, связи между заявками, суть проекта.

Источник истины по продукту — `docs/` (см. «Документы» в конце). Код следует докам; расхождение — повод спросить, а не молча выбрать.

## Демо оценивают — ядро обязано работать

> Your web version must be deployed and publicly available.
> Judges — and optionally other teams — will test it on their own laptops and phones.
> The demo is part of the presentation and is graded.

Что из этого следует:

- Стенд публичный, по HTTPS, открывается с ноутбука и с телефона.
- Ядро настоящее: оценка, разрешения, граф, сеть, модели, дела, журнал. Имитируются только системы банка вокруг узла.
- Проверяющие вводят свои данные. На любой корректный ввод система отвечает осмысленно, на некорректный — понятной ошибкой. Без падений, пустых экранов и заглушек.
- Готовые сценарии трёх зон запускаются в один клик, рядом — свой ввод.
- Несколько проверяющих работают одновременно, и их действия не ломают демо друг другу.
- Состояние демо можно вернуть к исходному.
- Решение по зелёной заявке — секунды.
- Перед каждой выкладкой — прогон сценариев на стенде с телефона и с ноутбука.

## Правила работы

1. **Объём не урезаем без согласования.** Всё из `docs/` входит в объём. Время на реализацию — не ограничение. Предложение убрать или упростить что-то — сначала вопрос владельцу.
2. **Никакого хардкода без ведома владельца.** Пороги, лимиты, веса, параметры генератора, суммы, сроки, тексты, адреса, ключи, справочники — не в коде. Они живут в конфигурации, сидах или БД, с версией. Если значение нужно выбрать — сперва спросить: предлагать пачкой, с обоснованием и источником. Хардкод — только по прямому указанию владельца, место помечается.
3. **Фронт ничего не считает и не зашивает.** Уровни, причины, статусы, сроки, справочники, демо-данные — только с бэка. Моков на фронте нет.
4. **Данные — в своей БД (PostgreSQL).** Никакого хранения в JSON-файлах или localStorage. Исключение — удобства интерфейса одного зрителя (последняя открытая вкладка, свёрнутая панель).
5. **Чистый код и нормальная архитектура обязательны**, даже в хакатоне (раздел «Код»).
6. Документы и тексты интерфейса — по-русски.
7. **Запуск и проверки — через Docker** (`compose.yaml`): стенд — `docker compose up --build -d`, тесты — `docker compose --profile test run --rm tests` (код монтируется томом, пересборка — только при смене зависимостей). Сервисы по одному на хосте не поднимаем.
8. **Темп хакатона.** Тесты — на ядро и на то, что может сломаться; без дублирующих проверок одного и того же. Полный прогон — один раз перед коммитом, в ходе работы — только затронутые тесты.

## Интерфейс

1. Белый и чёрный. Без эмодзи, неона, градиентов, свечения, стеклянных эффектов. Без типового «AI B2B SaaS» вида: без hero-баннеров, декоративных иллюстраций и плиток-метрик ради метрик.
2. Скругление 20px — у карточек, кнопок, полей ввода, выпадающих списков, модальных окон. Мелкие бейджи и чипы — полностью скруглённые.
3. Анимации только спокойные: плавные переходы 150–250 мс по opacity и transform. Без ярких, прыгающих и бесконечных анимаций. `prefers-reduced-motion` уважается.
4. Чистые экраны. Каждой роли — только то, что нужно для её решения. Без лишних блоков, данных «на всякий случай» и повторов.
5. Цвет — только для состояний: уровни, статусы, успех и ошибка. Никогда для декора, без радуги. Палитра — системная iOS (токены ниже). Категории различаются оттенками серого. Исключение по указанию владельца — знак продукта: «Anora Nazar» жирным, «Anora» красным, без иконки. Акцент основной кнопки — токен `--color-accent`, по умолчанию чёрный; акцент банка меняется в нём.
6. Иконки — одна библиотека: `lucide-react`. Эмодзи нигде нет: ни в интерфейсе, ни в текстах, ни в логах.
7. Интерфейс на русском. Все строки — в словаре `frontend/src/shared/i18n/ru.ts`, чтобы потом добавить узбекский.
8. Адаптивность сразу. Каждый экран работает от 360px до широкого монитора. Без фиксированных ширин раскладки в пикселях; брейкпоинты, отступы и размеры — токены. Экран сдаётся после проверки на 390px и 1440px.
9. Понятные названия и пути страниц (таблица «Роли и страницы»). Путь отражает роль и сущность.
10. Шрифт — Wix Madefor (Text — интерфейс, Display — крупные заголовки), файлы в сборке через `@fontsource`; запасной — системный стек. Суммы — табличными цифрами.

## Архитектура

Контейнеры C4 L2 из Блока 1 — логическое деление. В коде узел — один процесс FastAPI `node` с модулями. Реплика базы и по два экземпляра служб — только в целевом состоянии. Сервисы общаются только по HTTP и событиям, в чужую базу никто не ходит.

| Сервис | Код | Что делает |
| --- | --- | --- |
| `node` | `backend/src/node` | узел Anora Nazar — продукт: решения, разрешения, приём событий, индекс связей, скоринг, дела, журнал |
| `bank-sim` | `backend/src/bank_sim` | имитатор банка-пилота: приложение заёмщика, конвейер, АБС, второй филиал, внешние источники, сессии, карты, единая платформа программ, сценарии, кнопки сбоев; кредиторы Б и В — генераторы событий в сеть |
| `network-operator` | `backend/src/network_operator` | оператор сети кредиторов: ключ OPRF, счётчики, результаты проверок |
| `anchor` | `backend/src/anchor` | внешнее хранилище подписанных контрольных точек журнала (другой владелец) |
| `web` | `frontend` | интерфейс всех ролей |
| `postgres` | — | PostgreSQL, своя база у каждого сервиса |
| `world` | `backend/src/world` | генератор синтетического мира (команда, не сервис) |

Принципы:

1. **Узел решает, банк исполняет.** Зачисление (Т2) и оплата поставщику (Т5) — только по разрешению на операцию, которое АБС запрашивает прямо перед проводкой. На первом переводе (Т3) узел даёт рекомендацию, решает транзакционный антифрод банка. Граница — настоящий HTTP между `bank-sim` и `node`.
2. **В узле нет демо-кода.** Сценарии, сбои и свой ввод проверяющих живут в `bank-sim`.
3. **Узел получает данные только через свои интерфейсы** — вызовы Т1–Т6 и события. Генератор не пишет в базу узла: история прогоняется через `bank-sim`.
4. **Один факт — один владелец** (таблица владения — Блок 1). Остальные хранят ссылку или неизменяемый снимок.
5. **Сбой — не зелёный. Повтор безопасен** (ключи идемпотентности). Узел исключает повторную авторизацию одной бизнес-операции; единственность проводки — совместный контракт с АБС. **Решение воспроизводимо** (снимок входа и версии признаков, моделей, правил, политики).
6. **Сеть — отдельный адаптер, выключен по умолчанию.** Узел полностью работает без неё. В сеть уходят только ослеплённые токены и счётчики.
7. **Один код признака для обучения и для решения**, по времени получения данных банком (point-in-time).
8. **Факты, гипотезы и подтверждения хранятся раздельно.** Роль участника и метка появляются только по итогам проверки.

## Песочница на посетителя

Проверяющие работают одновременно и не мешают друг другу.

- Общий синтетический мир — один контур данных; у каждого посетителя — своя песочница, отдельный контур.
- Посетитель видит общий мир и только свои записи; чужих песочниц не видит. Общий мир посетители не меняют.
- Контур есть у всех данных во всех сервисах: заявки, события, индекс связей, разрешения, дела, журнал, сеть.
- Журнал — отдельная цепочка на контур: подделка записи в своей песочнице не ломает чужие.
- Сброс демо — удаление своей песочницы. Брошенные песочницы удаляются по сроку.
- В продакшне контур один — банк.

## Ядро: технические правила

1. **Решение — чистая функция** `decide(snapshot, features, models, policy) → Decision`: без запросов наружу и без `now()`. Ответы бюро, сессий, индекса и сети собираются до вызова. Отсюда машина времени, предсказуемые тесты и режим «без модели».
2. **Резерв — одна транзакция.** `SELECT … FROM applications WHERE id = :app FOR UPDATE`; проверки: версия та же, нет пометки «нужна новая оценка», оценка в сроке годности, нет активных удержаний, по «заявка + тип операции + транш» нет reserved, unknown или executed; затем вставка разрешения, запись в журнал и outbox — в той же транзакции. Read Committed достаточно.
3. **Приём события — своя транзакция**, ставит `needs_reassessment = true` найденным заявкам. Обе транзакции блокируют одну строку — порядок решает PostgreSQL. Несколько заявок блокируются строго по возрастанию id. Метрики: задержка «событие получено → пометка» и счётчик «сигнал пришёл уже после резерва».
4. **Защита от повторов — в базе.** Таблица ключей: ключ, хеш параметров, сохранённый ответ; тот же ключ с другими параметрами — 409. Частичный уникальный индекс на «заявка + тип операции + транш» для reserved, unknown, executed. Фоновая задача переводит просроченный reserved в unknown и сверяется с АБС.
5. **Два времени у каждого факта:** `occurred_at` и `received_at`. Функции признаков принимают `as_of` и берут только факты с `received_at <= as_of`; те же функции — в решении и в обучении. Генератор выдаёт поздние жалобы и исправления.
6. **Запись решения не меняется после создания** (JSONB): версия заявки, значения признаков с версией набора, ответы источников и сети, агрегаты графа, версии моделей, правил и порогов, сработавшие правила и причины.
7. **Причины — коды, не текст:** `{code, typology, source: rule|model|graph|network, evidence: [...], norm: "п. 44"}`. Каталог кодов — из сигналов Блоков 2–3; тексты — отдельно.
8. **Правила и пороги — YAML-файлы с версией**, у каждого правила ссылка на пункт нормы. Уровень — максимум из четырёх источников. Групповой флаг сам по себе не причина отказа. Удержание ставится на заявку, дело только объединяет заявки.
9. **Режим «без модели» — первым.** Это и резервная политика при сбое модели, и способ запустить весь путь до обучения. Реестр не запускает модель с чужим контрактом признаков и пишет причину «без модели». Выдуманный балл — это хардкод, его нет.
10. **Журнал:** хеш записи = H(хеш предыдущей ‖ канонический JSON по RFC 8785); один писатель в той же транзакции под advisory lock; контрольная точка — корень Меркла, подпись Ed25519 ключом из файла, отправка в `anchor`; проверка показывает первую изменённую запись.
11. **Симулятор банка ходит в узел только через API** по API-ключам с правами: конвейер — оценки, АБС — разрешения и итоги, источники — события. Кнопки сбоев: «потерять итог», «повторить с другой суммой», «узел недоступен», «очередь отстаёт».
12. **Сеть — последней.** Один полноценный узел (банк A) и оператор сети; банки Б и В — генераторы событий в симуляторе с тем же клиентом OPRF.

## Код

Бэкенд каждого сервиса — модульный монолит. Модуль — папка в `modules/` с одинаковым набором файлов:

| Файл | Что внутри |
| --- | --- |
| `api.py` | роутер: валидация, права, вызов сервиса; без бизнес-логики |
| `schemas.py` | Pydantic-схемы входа и выхода API |
| `service.py` | сценарии использования модуля, границы транзакций |
| `domain.py` | чистая логика без ввода-вывода |
| `repository.py` | доступ к БД |
| `models.py` | таблицы SQLAlchemy |

Зависимости идут в одну сторону: `api → service → domain / repository → models`. Модули общаются через сервисы друг друга или события, никогда через чужие репозитории и таблицы. Общий код без доменной логики — `backend/src/shared`.

Фронтенд — слои `app → pages → widgets → features → entities → shared`, импорт только вниз.

Общие правила:

- Типы везде: mypy и TypeScript strict; `Any` только с причиной.
- Имена в коде — английские и говорящие. Тексты интерфейса — только из словаря.
- Функция делает одно дело. Без дублирования, мёртвого кода и закомментированных кусков.
- Комментарий — только там, где неочевидно «почему».
- Ошибки типизированы и понятны пользователю. Ничего не глотаем молча.
- Схема БД меняется только миграциями Alembic.
- Конфигурация — из окружения и файлов конфигурации. Секреты — только из окружения; в репо — `.env.example`.
- Ядро покрыто тестами: правила, сведение в уровни, разрешения и их переходы, идемпотентность, журнал, OPRF, признаки point-in-time.
- Перед коммитом: `ruff`, `mypy`, `pytest`, `eslint`, `tsc`, сборка фронта.
